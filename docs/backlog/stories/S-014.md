# S-014 — Regras: uma família por usuário

**Marco:** M1 · **Deps:** S-008 · **Estimativa:** ≤2h, ≤4 arquivos

## Ler antes (somente estes)
- docs/adr/0003-firestore-model-and-rules.md ("uma família por usuário no MVP")
- docs/rules/firestore.md, docs/rules/testing.md

## Objetivo
Hoje um usuário que já tem família consegue criar outra ou entrar em outra (o cliente checa, as regras não). As regras passam a garantir uma família por usuário.

## Critérios de aceite (todos via `pnpm test:rules`)
1. AC1: `users/{uid}.familyId` só muda de `null` para um id (onde o uid é membro); de `F1` para `F2` e de `F1` para `null` são negados.
2. AC2: criar família exige, no mesmo batch, `users/{uid}.familyId` passar de `null` para o novo id (`get` antes == null, `getAfter` == familyId). Criar sem atualizar o perfil é negado; usuário com família criando outra é negado.
3. AC3: entrar (batch de S-008) exige o mesmo: perfil antes com `familyId == null` e depois == família. Entrar sem atualizar o perfil é negado; usuário com família entrando em outra é negado.
4. AC4: os casos permitidos de S-007/S-008 continuam passando (criar e entrar com perfil `familyId: null`).
5. AC5: `pnpm test:data` continua verde (o cliente já grava o perfil no mesmo batch).

## Fora de escopo
- Sair ou trocar de família, remover membro.

## Notas técnicas
- Arquivos: `firestore.rules`, `tests/rules/users.test.ts`, `tests/rules/families.test.ts`, `tests/rules/join.test.ts`.
- Helpers `createFamily` dos testes passam a incluir `b.update(users/{uid}, { familyId })` e semear `users/{uid}` com `familyId: null`.
- Perfil inexistente ⇒ negado (o cliente roda `ensureUserProfile` no login).
