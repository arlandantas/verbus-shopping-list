## Objetivo
Um código vazado dá acesso para sempre. Qualquer membro pode gerar um novo código na aba Família; o antigo deixa de funcionar.

## Critérios de aceite (cada um testável automaticamente)
1. AC1 (regras): membro atualiza `families/{id}` mudando só `inviteCode` para um código válido cujo convite novo existe no mesmo lote (`getAfter`), é da família e foi criado por ele; permitido.
2. AC2 (regras): mudar `inviteCode` junto com qualquer outro campo, para convite de outra família, ou sendo não membro é negado.
3. AC3 (regras): entrar com o código antigo, depois da rotação, é negado (convite antigo apagado no mesmo lote).
4. AC4 (dados, emulador): `rotateInviteCode(familyId)` em `src/data/` faz o lote (cria convite novo, atualiza família, apaga antigo) e devolve o código novo.
5. AC5 (E2E): na aba Família, "Gerar novo código" abre diálogo de confirmação; ao confirmar, o código mostrado muda; join com o antigo mostra erro.
6. AC6: strings pt-BR no módulo de strings; `pnpm check` verde.

## Fora de escopo
- Expiração automática, remover membros.

## Notas técnicas
- Regra: em `families` `allow update: if validJoin(familyId) || validRotate(familyId);` com `affectedKeys().hasOnly(['inviteCode'])`, `isMember`, `validCode` e `getAfter(invites/novo)`.
- Em `invites` o `delete` continua só para membro; o lote é online-only aceitável (ação rara), mas sem transação (ADR-0004).
- Gerador de código já existe (S-009); reutilizar.
